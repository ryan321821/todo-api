## 1. 为什么要重构？

重构前的代码结构是这样的：

```
app/
├── database.py    # 数据库连接 + 会话 + get_db 全部塞在一个文件里
├── models.py      # 所有 ORM 模型写在一个文件里
├── schemas.py     # 所有 Pydantic 模型写在一个文件里
└── main.py        # 应用初始化 + 所有路由函数 + 生命周期全部写在一个文件里
```

这种"平铺式"结构在只有一两个模型时完全够用。但是当你要添加更多功能模块（比如用户管理、便签模块、分类管理）时，问题就出来了：

| 问题 | 具体表现 |
| :--- | :--- |
| **文件臃肿** | `main.py` 同时包含应用初始化 + 所有路由 + 所有业务逻辑，代码越来越长 |
| **职责不清** | 数据库操作（查询、过滤）直接写在路由函数里，路由函数既负责接收请求又负责操作数据库 |
| **难以复用** | 如果另一个路由也需要"按 ID 查任务"，只能重复写 `db.query(Task).filter(...)` |
| **扩展困难** | 新增一个模块（如用户认证），所有代码都要往同一个 `main.py` 里堆 |
| **不支持版本化** | 没有 `/api/v1/` 这种版本前缀，未来想出 v2 版本时很难兼容 |

**重构后的企业级分层架构**解决了以上所有问题：每一层只做一件事，职责清晰，扩展方便。

## 2. 重构前后目录对比

### 重构前（4 个文件）

```text
app/
├── __init__.py
├── database.py       ← 数据库配置 + 会话 + get_db
├── models.py         ← 所有 ORM 模型
├── schemas.py        ← 所有 Pydantic 模型
├── main.py           ← 应用入口 + 全部路由 + 全部业务逻辑
└── test.py           ← 计算器 GUI（跟项目无关）
```

### 重构后（分层结构）

```text
app/
├── __init__.py
│
├── core/                  ← 【新增层】配置与安全
│   ├── __init__.py
│   ├── config.py          ← 原来硬编码在 database.py 里的配置 → 集中到这里
│   └── security.py        ← 【新增】密码加密与 JWT 工具（为将来做准备）
│
├── db/                    ← 【新增层】数据库连接
│   ├── __init__.py
│   ├── base_class.py      ← 原来 database.py 里的 Base = declarative_base()
│   ├── session.py         ← 原来 database.py 里的 engine、SessionLocal、get_db
│   └── base.py            ← 【新增】集中导入所有 ORM 模型，方便建表
│
├── models/                ← 【拆分自】原来的 models.py
│   ├── __init__.py
│   └── task.py            ← Task 模型（和原来一模一样的代码）
│
├── schemas/               ← 【拆分自】原来的 schemas.py
│   ├── __init__.py
│   ├── msg.py             ← MessageResponse（从原来 schemas.py 拆出来的）
│   └── task.py            ← TaskCreate/TaskUpdate/TaskResponse/TaskListResponse
│
├── crud/                  ← 【新增层】数据库操作逻辑
│   ├── __init__.py
│   ├── base.py            ← 通用的增删改查基类
│   └── crud_task.py       ← Task 专属的查询方法（从原来 main.py 路由里拆出来的）
│
├── api/                   ← 【拆分自】原来 main.py 里的路由函数
│   ├── __init__.py
│   └── v1/
│       ├── __init__.py
│       ├── api.py         ← 把所有子路由汇聚在一起
│       └── endpoints/
│           ├── __init__.py
│           ├── health.py  ← 原来 main.py 里的 root()、healthz()、health_check()
│           └── tasks.py   ← 原来 main.py 里的 create_task()、read_tasks() 等
│
└── main.py                ← 只负责：创建 app、挂载中间件、注册路由、管理生命周期
```

## 3. 核心设计思想：分层架构

整个架构分为 **6 层**，每一层只做一件事，上层调用下层，下层不知道上层的存在：

```text
┌─────────────────────────────────────────┐
│           app/main.py                   │  ← 最顶层：创建应用、注册路由
│  （应用入口：FastAPI 实例 + 中间件）       │
└───────────────────┬─────────────────────┘
                    │ include_router(api_router)
                    ▼
┌─────────────────────────────────────────┐
│        app/api/v1/endpoints/            │  ← 第 1 层：路由控制器（Controller）
│  health.py  tasks.py                    │  接收 HTTP 请求 → 调用 crud 层
└───────────────────┬─────────────────────┘
                    │ crud.task.create(...) / crud.task.get(...)
                    ▼
┌─────────────────────────────────────────┐
│           app/crud/                     │  ← 第 2 层：数据持久层（DAO/Service）
│  base.py（通用CRUD）crud_task.py        │  封装数据库操作逻辑
└───────────────────┬─────────────────────┘
                    │ db.query(Task).filter(...) / db.add(...) / db.commit()
                    ▼
┌─────────────────────────────────────────┐
│  app/models/ + app/db/                  │  ← 第 3 层：数据层
│  task.py（ORM模型）session.py（会话）     │  定义表结构 + 管理数据库连接
└─────────────────────────────────────────┘

辅助层（被所有层使用）：
┌─────────────────────────────────────────┐
│  app/core/config.py                     │  ← 全局配置（数据库URL、项目名等）
│  app/schemas/ (task.py, msg.py)         │  ← 数据校验（请求/响应格式定义）
└─────────────────────────────────────────┘
```

**一句话总结**：请求进来 → 路由层接住 → 调用 CRUD 层操作数据库 → 数据通过 Schema 校验后返回。

## 4. 逐层拆解：每个文件的作用与调用关系

### 4.1 配置层 `app/core/`

#### `app/core/config.py` —— 全局配置中心

**原来在哪**：之前硬编码在 `database.py` 的 `os.environ.get("DATABASE_URL", "...")` 里。

**现在做了什么**：用 `pydantic-settings` 的 `BaseSettings` 类把所有配置集中管理：

```python
class Settings(BaseSettings):
    PROJECT_NAME: str = "迷你任务备忘录 API"     # 项目名称
    DATABASE_URL: str = "mysql+pymysql://..."    # 数据库连接串
    SECRET_KEY: str = "change-me-in-production"  # JWT 密钥
    API_V1_STR: str = "/api/v1"                  # API 版本前缀
    STATIC_DIR: str = "static"                   # 静态文件目录路径
```

**好处**：
- 所有配置在一个地方，不用到处找
- 自动从环境变量读取值（docker-compose.yml 设置的 `DATABASE_URL` 会自动覆盖默认值）
- 有类型检查，写错了会报错

**谁在用它**：几乎所有模块都通过 `from app.core.config import settings` 来读取配置。

#### `app/core/security.py` —— 安全加密工具

**原来有没有**：没有，这是新增的。

**为什么要加**：虽然当前项目还不需要用户登录，但企业级项目一定会用到密码哈希和 JWT 令牌。提前搭好框架，后面加用户模块时直接用。

**包含功能**：
- `get_password_hash()` → 给密码加密
- `verify_password()` → 验证密码
- `create_access_token()` → 生成 JWT 登录令牌
- `decode_access_token()` → 解析 JWT 令牌

---

### 4.2 数据库层 `app/db/`

这一层对应原来的 `database.py`，被拆成了 3 个小文件：

#### `app/db/base_class.py` —— ORM 基类定义

```python
Base = declarative_base()
```

就这一行。原来写在 `database.py` 里的 `Base`，现在独立出来。

**为什么要独立**：因为 `Base` 被 `models/` 和 `db/` 两个地方同时需要，独立出来避免循环导入。

#### `app/db/session.py` —— 数据库连接与会话

**原来在哪**：`database.py` 里的 `engine`、`SessionLocal`、`get_db()`。

**代码完全等价**，只是改为从 `settings` 读取连接串：

```python
# 原来（database.py）：
SQLALCHEMY_DATABASE_URL = os.environ.get("DATABASE_URL", "...")
engine = create_engine(SQLALCHEMY_DATABASE_URL, ...)

# 现在（db/session.py）：
engine = create_engine(settings.DATABASE_URL, ...)  # 从 config 统一读取
```

#### `app/db/base.py` —— ORM 模型汇总注册

```python
from app.db.base_class import Base       # 导入基类
from app.models.task import Task         # 导入 Task 模型
```

**作用**：启动时 `main.py` 执行 `Base.metadata.create_all(bind=engine)` 建表。
Python 的工作原理是：**只有被导入过的模型，`Base.metadata` 才能"看到"它**。
所以这个文件的唯一作用就是确保所有模型都被导入了。

> 未来你新增模型（比如 `User`），只需要在这个文件里加一行 `from app.models.user import User` 就行。

---

### 4.3 ORM 模型层 `app/models/`

#### `app/models/task.py` —— Task 数据表模型

**原来在哪**：`models.py`（整个文件搬过来，代码一模一样）。

**唯一变化**：导入 `Base` 的路径变了：

```python
# 原来：from .database import Base
# 现在：from app.db.base_class import Base
```

表结构、字段定义、`__repr__` 方法完全没变。

#### `app/models/__init__.py` —— 模型导出

```python
from .task import Task
```

**作用**：让其他模块可以直接写 `from app.models import Task`，不用写完整路径。

---

### 4.4 数据校验层 `app/schemas/`

#### `app/schemas/task.py` —— Task 请求/响应 Schema

**原来在哪**：`schemas.py` 里的 `TaskCreate`、`TaskUpdate`、`TaskResponse`、`TaskListResponse`。

代码完全一样，只是搬到了独立文件里。

#### `app/schemas/msg.py` —— 通用消息响应

**原来在哪**：`schemas.py` 里的 `MessageResponse`。

拆出来是因为 `MessageResponse` 不只属于 Task 模块——将来删除用户、删除便签都会用到它。

#### `app/schemas/__init__.py` —— Schema 导出

```python
from .msg import MessageResponse
from .task import TaskCreate, TaskListResponse, TaskResponse, TaskUpdate
```

**作用**：让其他模块可以直接写 `from app.schemas import TaskCreate, TaskResponse`。

### 4.5 数据持久层 `app/crud/`

**这是完全新增的一层**，也是重构的最大亮点。

#### 原来是怎么做的（直接在路由里操作数据库）

```python
# 原来 main.py 里的路由函数：
@app.post("/tasks", ...)
def create_task(task: TaskCreate, db: Session = Depends(get_db)):
    db_task = Task(title=task.title, description=task.description, priority=task.priority)
    db.add(db_task)        # ← 数据库操作直接写在路由里
    db.commit()            # ← 路由函数同时负责"接收请求"和"操作数据库"
    db.refresh(db_task)
    return db_task
```

#### 现在怎么做（路由调用 CRUD 层）

```python
# 现在 api/v1/endpoints/tasks.py 里的路由函数：
@router.post("", ...)
def create_task(task_in: TaskCreate, db: Session = Depends(get_db)):
    return crud.task.create(db=db, obj_in=task_in)  # ← 一行搞定，数据库操作交给 crud 层

# 数据库操作在 crud/base.py 里：
def create(self, db, *, obj_in):
    obj_in_data = obj_in.model_dump()
    db_obj = self.model(**obj_in_data)
    db.add(db_obj)
    db.commit()
    db.refresh(db_obj)
    return db_obj
```

#### `app/crud/base.py` —— 通用 CRUD 基类

提供 4 个基础方法，**所有模型都能复用**：

| 方法 | 作用 | 对应 SQL |
| :--- | :--- | :--- |
| `get(db, id)` | 按 ID 查单条 | `SELECT * FROM tasks WHERE id = ?` |
| `get_multi(db, skip, limit)` | 分页查多条 | `SELECT * FROM tasks LIMIT ? OFFSET ?` |
| `create(db, obj_in)` | 创建记录 | `INSERT INTO tasks ...` |
| `update(db, db_obj, obj_in)` | 更新记录 | `UPDATE tasks SET ... WHERE id = ?` |
| `remove(db, id)` | 删除记录 | `DELETE FROM tasks WHERE id = ?` |

#### `app/crud/crud_task.py` —— Task 专属 CRUD

继承 `CRUDBase`，额外增加了一个 `get_multi_with_filter()` 方法：

```python
class CRUDTask(CRUDBase[Task, TaskCreate, TaskUpdate]):
    def get_multi_with_filter(self, db, *, skip, limit, is_completed, priority):
        # 动态筛选 + 倒序排列 + 分页 + 统计总数
        ...
        return total, tasks
```

**原来这段逻辑在哪**：在 `main.py` 的 `read_tasks()` 路由函数里。
现在路由只负责"接收参数 → 调用 crud → 返回结果"，数据库查询逻辑全部在 crud 层。

#### `app/crud/__init__.py` —— 导出 CRUD 实例

```python
from .crud_task import task   # task 是 CRUDTask(Task) 的实例
```

**使用方式**：`import crud` 然后 `crud.task.get(db, id=1)`、`crud.task.create(db, obj_in=...)`。

### 4.6 路由控制层 `app/api/`

**原来在哪**：所有路由函数都堆在 `main.py` 里。

**现在拆成了**：

#### `app/api/v1/endpoints/health.py` —— 系统路由

包含 3 个路由函数（和原来 `main.py` 里完全一样的功能）：

| 路由 | 函数 | 原来在 |
| :--- | :--- | :--- |
| `GET /` | `root()` | main.py 第 58-61 行 |
| `GET /healthz` | `healthz()` | main.py 第 64-67 行 |
| `GET /health` | `health_check()` | main.py 第 70-77 行 |

#### `app/api/v1/endpoints/tasks.py` —— 任务路由

包含 5 个路由函数（功能和原来一样，但数据库操作改为调用 crud 层）：

| 路由 | 函数 | 原来在 |
| :--- | :--- | :--- |
| `POST /tasks` | `create_task()` | main.py 第 83-94 行 |
| `GET /tasks` | `read_tasks()` | main.py 第 97-119 行 |
| `GET /tasks/{task_id}` | `read_task()` | main.py 第 122-128 行 |
| `PUT /tasks/{task_id}` | `update_task()` | main.py 第 131-145 行 |
| `DELETE /tasks/{task_id}` | `delete_task()` | main.py 第 148-157 行 |

> 注意 `tasks.py` 里路由路径写的是 `""` 而不是 `"/tasks"`。
> 这是因为在 `api.py` 里挂载路由时已经指定了 `prefix="/tasks"`，
> 路由函数里的路径会自动拼接上这个前缀。

#### `app/api/v1/api.py` —— 路由汇聚（相当于"路由总线"）

```python
api_router = APIRouter()
api_router.include_router(health.router, tags=["系统"])        # /、/healthz、/health
api_router.include_router(tasks.router, prefix="/tasks", tags=["任务"])  # /tasks/...
```

**作用**：把所有子模块的路由合并到一个 `api_router` 里，然后交给 `main.py` 统一注册。

> 未来你要加用户模块，只需要：
> 1. 创建 `endpoints/users.py` 写路由
> 2. 在 `api.py` 里加一行 `api_router.include_router(users.router, prefix="/users", tags=["用户"])`

### 4.7 应用入口 `app/main.py`

**原来**：包含应用初始化 + 静态文件挂载 + 8 个路由函数 = 158 行代码。

**现在**：只负责 4 件事 = 约 60 行代码：

1. **创建 FastAPI 实例**（从 `settings` 读取项目名称、描述、版本号）
2. **配置 CORS 中间件**（允许跨域访问，前后端分离必备）
3. **挂载静态文件**（`/static/index.html` 前端页面）
4. **注册路由**（两次挂载 `api_router`）：
   - 直接挂在根路径 → 保证 `/tasks`、`/health` 等原有路径继续可用
   - 挂在 `/api/v1` 前缀 → 同时支持 `/api/v1/tasks` 企业级路径

## 6. 模块间调用关系全局图

一个请求从浏览器到数据库再回来，经过的完整链路：

```text
浏览器发起请求：POST http://localhost:8000/tasks
                         │
                         ▼
              ┌──── app/main.py ────┐
              │  FastAPI 应用实例    │
              │  路由分发到 api_router│
              └─────────┬──────────┘
                        │
                        ▼
           ┌── app/api/v1/api.py ──┐
           │  匹配到 prefix="/tasks" │
           │  → endpoints/tasks.py  │
           └────────────┬──────────┘
                        │
                        ▼
    ┌── app/api/v1/endpoints/tasks.py ──┐
    │                                    │
    │  def create_task(task_in, db):     │  ← 路由函数
    │    ① Pydantic 自动校验 task_in     │  ← 用 app/schemas/task.py 的 TaskCreate
    │    ② db 由 Depends(get_db) 注入    │  ← 用 app/db/session.py 的 get_db()
    │    ③ return crud.task.create(...)  │  ← 调用 app/crud/crud_task.py
    │                                    │
    └────────────┬───────────────────────┘
                 │
                 ▼
      ┌── app/crud/base.py ──┐
      │                       │
      │  def create(db, obj_in):        │
      │    data = obj_in.model_dump()   │  ← Pydantic 模型转成字典
      │    db_obj = Task(**data)        │  ← 用 app/models/task.py 的 Task
      │    db.add(db_obj)               │  ← SQLAlchemy 操作
      │    db.commit()                  │  ← 提交到 MySQL
      │    db.refresh(db_obj)           │  ← 拿回自增 ID 和时间戳
      │    return db_obj                │  ← 返回 ORM 对象
      │                       │
      └───────────┬───────────┘
                  │
                  ▼
    ┌── app/models/task.py ──┐
    │  class Task(Base):     │  ← ORM 模型映射到 MySQL 的 tasks 表
    │    id, title, ...      │
    └────────────────────────┘
                  │
                  ▼
            ┌── MySQL ──┐
            │ tasks 表   │
            └────────────┘

返回时：ORM 对象 → Pydantic TaskResponse 自动序列化 → JSON 响应 → 浏览器
```

## 7. 接口兼容性说明

**所有原有的接口路径完全不变**，前端页面 `index.html` 零修改即可工作：

| 接口 | 原来的路径 | 重构后仍然可用 | 新增的企业级路径 |
| :--- | :--- | :--- | :--- |
| 欢迎 | `GET /` | ✅ `GET /` | `GET /api/v1/` |
| 健康检查 | `GET /healthz` | ✅ `GET /healthz` | `GET /api/v1/healthz` |
| 数据库检查 | `GET /health` | ✅ `GET /health` | `GET /api/v1/health` |
| 创建任务 | `POST /tasks` | ✅ `POST /tasks` | `POST /api/v1/tasks` |
| 任务列表 | `GET /tasks` | ✅ `GET /tasks` | `GET /api/v1/tasks` |
| 任务详情 | `GET /tasks/{id}` | ✅ `GET /tasks/{id}` | `GET /api/v1/tasks/{id}` |
| 更新任务 | `PUT /tasks/{id}` | ✅ `PUT /tasks/{id}` | `PUT /api/v1/tasks/{id}` |
| 删除任务 | `DELETE /tasks/{id}` | ✅ `DELETE /tasks/{id}` | `DELETE /api/v1/tasks/{id}` |
| 前端页面 | `/static/index.html` | ✅ `/static/index.html` | — |

**实现原理**（在 `main.py` 里）：

```python
# 第一次挂载：不加前缀 → 保证 /tasks 仍然可用
app.include_router(api_router)

# 第二次挂载：加 /api/v1 前缀 → 同时支持 /api/v1/tasks
app.include_router(api_router, prefix=settings.API_V1_STR)
```
